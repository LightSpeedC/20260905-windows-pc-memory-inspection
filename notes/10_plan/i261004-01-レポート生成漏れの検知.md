## 1. この計画について

### 目的

6 時間ごとのレポート生成が止まったとき、**人もセッションも介さずに**検知し、画面への通知とログで知らせる。あわせて、**起動の組み立て（いまの cmd の中身）を node（TypeScript）へ移し**、ログの文字コードを UTF-8 の 1 種類に揃える。

### きっかけ

2026-09-29 から 10-04 まで、約 22 回分のレポートが作られなかった。タスクスケジューラの履歴は「完了」のままで、気づいたのは約 5 日後だった。確認の手段は、セッションの中だけで動く cron の 1 本だけで、<strong>セッションが止まった間は、誰も見ていなかった。</strong>経緯と原因は課題 [i261004-01](../40_issues/issues.md) に書いた。

### この計画でやらないこと

- **生成タスクの登録の変更**。タスクが指す `tools/80_ops/inspect-process-memory.cmd` と引数 `nopause` は変えない（中身を node 呼び出しにするだけで、再登録は要らない）。実行時刻・実行ユーザーも変えない
- **`inspect-process-memory.ps1` の書き換え**。プロセス・メモリの取得は PowerShell が合っており、動作も確かめ済みのため、そのまま使う
- **検知用タスク自身が止まったことの検知**。検知の検知は作らない。生成と検知を別のタスクにして、同時に壊れる確率を下げるところまでにする

## 2. いまの状態

### 生成の所要時間（10-04 の実測）

| 区間 | 所要 |
|---|---|
| レポートの HTML が出るまで（ps1） | 約 10〜15 秒 |
| ch06 が書き終わるまで（`claude -p`） | 約 4 分半〜7 分半（4 分 33 秒・7 分 21 秒） |

5 分後に ch06 まで見ると、遅い日は誤報になる。**確認は生成予定の 15 分後にする**（いまのセッション cron と同じ :15）。

### 検知の手段（いま）

| 手段 | 弱点 |
|---|---|
| セッションの cron（毎 :15） | セッションの中でしか動かない。止まっていた間は発火しない。7 日で失効する |
| タスクスケジューラの履歴 | 即終了でも「完了・終了コード 0」に見える（終了コードは 10-04 に非 0 を返す形へ直した） |

## 3. 作るもの

### 言語の分担

起動の組み立てと検知を、<strong>node（TypeScript）</strong>で書く。`.ts` は node がそのまま実行する（この環境の node v26.10.0 で実測）。

| 役目 | 言語 | 理由 |
|---|---|---|
| 起動の組み立て（subst・カレント・ps1 と `claude -p` の起動・ログ・終了コード） | node（TypeScript） | ログを UTF-8 の 1 種類で書ける。cmd の `call` 漏れ・遅延展開・終了コードの癖が無くなる。`node:test` で先にテストを書ける |
| 検知（生成漏れの判定・ログ・通知の起動） | node（TypeScript） | ファイルを読むだけで、プロセス情報は使わない。テストできる |
| プロセス・メモリの取得（レポート生成） | PowerShell（既存の ps1） | Windows のプロセス情報の取得に合う。動作確認済みで、書き換える利点が無い |
| トースト通知 | PowerShell を呼ぶ | node に標準のトースト機能は無い。追加の npm パッケージを避け、`-EncodedCommand` で渡して、コードページに依存させない |
| 起動役（`inspect-process-memory.cmd`） | cmd（薄く） | `node` を呼んで終了コードを返すだけ。タスクの登録（このファイルを指す）を変えずに済む |

### 作るファイル

| ファイル | 内容 |
|---|---|
| `tools/80_ops/lib/` | 共有の部品。ログ（JST・ミリ秒・UTF-8・ユーザープロファイルの伏せ字）、引数の解釈、レポート判定の純粋な関数 |
| `tools/80_ops/inspect-process-memory.ts` | 起動の組み立て。いまの cmd の中身（引数 `nopause` `noai` `model:` `effort:` は同じ意味） |
| `tools/80_ops/check-report.ts` | 検知。`logs/check-report.log` に記録し、異常のときだけトーストを出す |
| `tests/*.test.ts` | `node:test` のテスト。`tools/40_test/run-tests.ps1` から一括で動かす |
| `tools/80_ops/register-check-task.ps1` | 検知用タスクの登録（管理者で実行）。既存の登録スクリプトと同じ形にする |

ログは 2 本に分ける。`logs/task-run.log`（生成の経過。`claude -p` の出力も入る）と `logs/check-report.log`（検知の結果）。**どちらも UTF-8 の 1 種類**で書く。

### 検知用のタスク

タスクスケジューラに、生成タスクとは別のタスクを足す。**毎日 0:15・0:45・6:15・6:45・12:15・12:45・18:15・18:45** に動き、次の 2 点を見る。

1. 直近の予定時刻（0・6・12・18 時）**以降に生成されたレポート**が `logs/reports-admin.txt` にあるか
2. そのレポートに `ch06` があるか

手動で作ったレポートは、予定時刻以降なら 1 に数える。「最終行が新しいか」ではなく「予定時刻以降のものがあるか」で見る。

#### 2 回の確認（10-04 に決定）

10-04 の 18:00 の分は、PC がスリープ中で、復帰した 18:17:59 に遅れて実行された。:15 に 1 回だけ確認すると、この遅れを**誤って異常**と判定する。このため、**:15 の異常は通知せず、:45 の再確認でもなお異常のときだけ通知する**。

| 時刻 | 異常のとき | ログの 1 行 |
|---|---|---|
| :15（最初の確認） | 通知しない | `⚠️ 再確認待ち …` |
| :45（再確認。:30 以降） | トースト通知する | `❌ 異常 …` |

最終かどうかは、確認した時刻の「分」で決める（30 分以降なら最終）。タスクは同じコマンドで、時刻だけが違う。

### 知らせ方

| 方法 | 内容 |
|---|---|
| ログ | `logs/` に、確認の時刻・結果・理由を 1 行ずつ追記する。**異常のときだけでなく、正常のときも残す**（検知用タスク自身が動いたことの証拠になる） |
| トースト通知 | 異常のときだけ、画面右下に出す。Windows PowerShell 5.1 から、追加のモジュールなしで出せる。**10-04 に実機で表示を確認した**。「ログを開く」ボタンで `check-report.log` を開く |

### 実行の条件

トーストは、**ユーザーがログオンしているデスクトップにしか出ない**と考えている（未確認）。生成タスクは「ログオンしているかどうかにかかわらず実行する」設定だが、検知用タスクは<strong>「ユーザーがログオンしているときのみ実行する」にする</strong>。ログオンしていないときは、ログだけが残る。

### 通知をクリックしたときの動作

| 動作 | 状態 |
|---|---|
| ログのファイルを開く（URI を起動する形） | ✅ **採用** （10-04 に実機で、ボタンからログが開くことを確認） |
| バッチ・スクリプトを実行する | ⬜ **採用しない** （独自プロトコルのレジストリ登録が要り、今回の目的に対して過大） |

ログの文字コードが混在していると、開いたときに化ける（10-04 に確認）。**UTF-8 の 1 種類に揃えるのは、このためでもある。**

## 5. 決めておくこととリスク

| 論点 | 扱い |
|---|---|
| 通知の見逃し | トーストは消える。ログに必ず残し、**セッションを開いたときに、最新の確認結果を読む**手順をローカルルールに書く（指示を受けてから） |
| ログオンしていない時間帯 | トーストは出ない。ログに残るので、次にログオンしたときに読める |
| 検知用タスクが止まる | 検知の検知は作らない。ログに「正常」も毎回残るため、記録が途切れていれば、後から分かる |
| 実行ユーザーのログイン期限切れ | 生成タスクが `Login expired` で失敗するのも、ch06 が無いこととして検知できる。原因の切り分けは生成側のログ（`logs/task-run.log`）で行う |
| node の前提 | `.ts` の直接実行には新しめの node が要る。この PC は v26.10.0 で、システム PATH（`C:\Tools\nodejs`）にあり、2 つの実行ユーザーとも見つかることをログで確認した。cmd はすでに `node -p` を使っており、新しい前提ではない |
| 動いている流れの置き換え | cmd の中身を node に替えるため、生成が止まる恐れがある。**実環境（タスク経由）で ch06 まで書かれることを確かめるまで、旧 cmd の中身を Git の履歴に残す**（戻せるようにする） |
| PowerShell 5.1 の出力 | ps1 の出力を node で受けると CP932 になる。**ps1 の出力は受けず、終了コードだけを見る**（画面には出る） |
